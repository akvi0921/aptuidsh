# 首版真机反馈与修复（v1.0.2 → v1.0.3）

## 用户反馈的四个现象

1. 首屏点「安装并启动」后无反应
2. 环境控制台无日志输出
3. 3081 端口没有启动
4. 点「官方 Web UI」APP 崩溃退出；原生 UI 点进去白屏

## 定位到的确定缺陷

### 缺陷 1（已确认，直接解释现象 4）：主线程网络调用

`WebUiActivity.kt` 在两处**在组合期/主线程**调用了探活：

```kotlin
val backendAlive = remember { DshBackend.get().probePort() }   // ← 组合期，主线程
...
if (!DshBackend.get().probePort()) { ... }                      // ← 按钮回调，主线程
```

`probePort()` 内部是 `new Socket().connect(...)`。Android 对主线程网络操作会抛
`NetworkOnMainThreadException` —— **一进「官方 Web UI」页就必崩**，与用户描述完全一致。

修复：`reload()` 改到 `Thread{}` 内探活；组合期的探活改成
`LaunchedEffect + withContext(Dispatchers.IO)`。

### 缺陷 2（结构性）：把长任务交给了 UI 的协程作用域

首版「安装并启动」的实现是：

```kotlin
scope.launch {                       // scope = rememberCoroutineScope()
    withContext(Dispatchers.IO) { backend.install(context) }
    ...
    busy = false                     // ← 只有这条路径能复位
}
```

两个问题：
- 一旦这个作用域被取消、或工作抛出异常，**界面上完全静默**：按钮没反应、没有任何日志；
- `busy` 只有走完全程才会复位，工作转交别处后就永久禁用按钮 —— 现象正是「点了没反应」。

修复：全部改为**由前台服务 `DshService` 在自己的 worker 线程执行**
（`requestInstallAndStart` / `requestStop` / `requestRestart` / `requestStart`），
界面只负责观察状态；`busy` 改为**由真实阶段推导**，不再依赖本地布尔量。

### 缺陷 3（可观测性）：控制台只看后端进程输出

`EnvConsoleScreen` 的日志区只绑定 `DshBackend.recentLog()`，而它**只填充 dsh 进程的 stdout**。
安装阶段（资源拷贝、tar 解压、校验）出任何问题，控制台都是**一片空白**——现象正是「无日志」。

修复：新增 `EnvLog`（内存环形缓冲 + `filesDir/logs/bootstrap.log` 落盘 + 监听器），
把**全过程**打进去：安装各阶段、镜像大小与可用空间、tar 命令行与退出码、
启动器自检结果、exec 命令行与 PID、dsh 每一行输出、**所有异常的完整栈**。

### 缺陷 4（埋点缺失）：崩溃无处可查

真机崩溃既没有 logcat 权限也没有落盘，完全无法定位。
修复：`AptuidshApp` 安装全局 `UncaughtExceptionHandler`，把完整堆栈写到两处用户可读位置：

- `Android/data/com.aptuidsh.kui/files/crash.txt`
- `/sdcard/APTUIDSH/crash.txt`（已授予「所有文件访问」时）

### 缺陷 5（潜在崩溃）：API 26 才有的方法用在 minSdk 24 上

`ProrootEnv.runCaptured` 用了 `Process.waitFor(long, TimeUnit)`，
该重载**需要 API 26**，而本 APP 的 `minSdk` 是 24，在 Android 7.x 上会 `NoSuchMethodError`。
修复：改成 `exitValue()` 轮询，避免版本依赖。

### 缺陷 6（潜在风险）：未压缩 asset 的读取路径

原先对 `rootfs.tar.xz` 设置了 `noCompress`（7 万次压缩比已经很低的 xz，再压一次无意义）。
但**未压缩 asset 在读取路径上存在设备相关的边缘行为**，而
`AssetManager.open(ACCESS_STREAMING)` 对 Deflated asset 是必然可用的。
修复：移除 `noCompress`，APK 体积几乎不变，换来安装环节的确定性。

### 另外加固的点

- `startForeground` 包 try/catch：某些 ROM/权限状态下它会抛异常，
  一旦抛出会把服务打死，表现同样是「点了没反应」。
- `DshBackend.install/start/stop` 全部包 `Throwable` 兜底，**绝不让异常逃到调用方**。
- 移除 `AptuidshApp.backendRunning()` —— 那是个「同步探活」陷阱，
  任何在组合期调用它的写法都会重演缺陷 1。

## 新增：不需要任何点击就能看到的「环境事实核查」

控制台顶部现在直接列出关键事实（`ProrootEnv.diagnose`）：

```
nativeLibraryDir = /data/app/.../lib/arm64
启动器存在 = true，可读 = true，可执行 = ?，大小 = 43624
nativeLibraryDir 条目数 = N
  libproroot.so 存在=true 可执行=?
  ...（其余 4 个）
rootfs 目录 = ...，存在 = ?
安装标记 = ?
关键文件: bin/sh=? node=? dsh=?
filesDir 可用空间 = NMB（安装约需 670MB）
需安装 = true
```

这样「卡在哪一步」一眼可见：**若「可执行 = false」，说明 Android 沙箱不允许执行该路径
（本方案的前置条件不成立）；若「nativeLibraryDir 条目数 = 0」，说明 .so 未被解包**。

## v1.0.4：追加定位到的崩溃点

用户确认「卡片上从未出现任何红色文字」。这一点很关键：
说明 `install()` 连「设置 INSTALLING 阶段」之后的**报错分支**都没走到，
最可能就是**进程直接被异常打死了**（v1.0.2 无崩溃捕获，重启后卡片回到「未安装」，
肉眼看起来就是「点了没反应」）。

顺着这条线找到最可能的击穿点：

### 缺陷 7：`assetSize()` 用 `ACCESS_UNKNOWN` 打开 77MB 资产

```java
try (InputStream in = ctx.getAssets().open(ROOTFS_ASSET, AssetManager.ACCESS_UNKNOWN)) {
    return in.available();      // ← 可能让 AssetManager 把整个资产映射/读入内存
}
```

- 对**未压缩**资产，`ACCESS_UNKNOWN` 会走 direct-buffer 路径；
- 由此可能抛 **`OutOfMemoryError`——它不是 `IOException`**；
- 而 v1.0.2 的 `DshBackend.install()` 只写了 `catch (IOException e)`，
  于是 OOM **直接击穿 `withContext` 协程 → 进程崩溃**。

修复（三重）：
1. `assetSize()` 改为**直接读 APK 的 zip 条目**（`ZipFile(sourceDir).getEntry("assets/…")`）——
   零内存、精确，结果已核对为 77825712 字节；
2. `install()` 增加 `catch (OutOfMemoryError)` 分支，给出「关闭其他应用后重试」的提示；
3. 兜底 catch 从 `IOException` 放宽到 `Throwable`，并把 `e.getMessage()` 换成 `e`（连类型一起显示）。

此外，尺寸未知时进度条不再静止不动（改为按已拷贝 MB 数刷新）。

### 为什么 v1.0.4 一定能给答案

即使还有别的意外，v1.0.4 也会**在界面上写出原因**，并把完整堆栈落到：

- 控制台「全过程日志」区（安装每一阶段 + 异常栈）
- 控制台顶部「环境事实核查」区（启动器是否可执行、nativeLibraryDir 条目数、空间等）
- `Android/data/com.aptuidsh.kui/files/crash.txt`（崩溃时）
- `/sdcard/APTUIDSH/crash.txt`（崩溃时）
