# 真机故障定位：安装时解压失败（v1.0.5 → v1.1.0）

## 用户提供的日志（决定性）

```
21:50:02.589 INFO  执行解压: /system/bin/tar -xJf .../rootfs.tar.xz (cwd=.../files/rootfs)
21:50:02.620 INFO  tar 退出码=0, 输出: tar: exec xz: No such file or directory
21:50:02.622 ERROR rootfs 校验失败: 缺少 bin/sh
```

## 根因 1：Android 的 toybox tar 不支持自带 xz

`toybox tar --help` 里写着 `J xz compression`，但那**不是内置实现**——
它会去 exec 外部 `xz` 程序，而 Android 系统里**根本没有 `/system/bin/xz`**：

```
$ ls /system/bin/xz /system/bin/gzip /system/bin/bzip2
ls: /system/bin/xz: No such file or directory
lrwxrwxrwx  /system/bin/gzip -> toybox      ← 内置
-rwxr-xr-x  /system/bin/bzip2              ← 独立二进制
```

**最阴险的地方：解压失败后 toybox 仍然返回退出码 0。**
（本次靠 `verifyLayout()` 校验关键文件才拦住，否则会带着一个空 rootfs 继续往下走。）

### 为什么开发阶段没发现

第一轮验证是在 Termux 里跑 `toybox tar -xJf` —— **Termux 的 PATH 里恰好有 `xz`**，
于是它 exec 成功、解压通过。**验证被环境污染了，结论是假的。**

干净的对照实验（`env -i PATH=/system/bin:/system/xbin`）：

| 命令 | 结果 |
|---|---|
| `tar -xzf`（gzip） | ✅ 成功，文件数与符号链接均正确 |
| `tar -xJf`（xz） | ❌ `tar: exec xz: No such file or directory`，0 个文件，**退出码 0** |

### 修复

镜像格式从 `xz` 改为 **gzip**（toybox 内置实现，零外部依赖）。
代价：镜像从 77.8MB 涨到 136.6MB，APK 从 88MB 涨到 166MB。
另外在 `RootfsInstaller` 里增加**输出扫描**：只要 tar 打印了 `tar: ` 就判失败，
不再信任退出码。

## 根因 2：AGP 会在构建期自动解压 `.gz` 后缀的 asset

改名为 `rootfs.tar.gz` 后第一次构建，APK 里出现的却是：

```
assets/rootfs.tar   553359360 bytes    ← 被解压了！
```

`mergeDebugAssets` 把 `.gz` 资产解压成了原始文件，APK 因此涨到 166MB 且多一次无谓的解压。
改用中性后缀 **`rootfs.img`** 绕开该行为（内容是 gzip，由 `tar -xzf` 显式指定 `-z` 解压）。

## 干净环境下的最终验证（v1.1.0）

```
导出 assets/rootfs.img (136645275 字节)
env -i PATH=/system/bin:/system/xbin /system/bin/tar -xzf rootfs.img -C rootfs
  → 32614 个文件，10.9 秒
guest 自检 → APTUIDSH-SMOKE-OK / dsh 0.1.5-rc.1
```

## 教训

1. **验证必须在与目标一致的环境里做**。宿主 shell 的 PATH 会悄悄补齐目标环境没有的东西，
   让失败的路径看起来是成功的。
2. **不要信任退出码**。toybox 在解压器缺失时返回 0；关键步骤必须校验产物本身。
3. 构建工具会做「聪明的」隐式处理（AGP 自动解压 `.gz`），关键资产要用中性命名并实测体积。
